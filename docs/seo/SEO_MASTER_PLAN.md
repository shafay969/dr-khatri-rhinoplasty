# SEO operating plan

This is the standing decision framework, not a completion ledger. Current tasks, findings, approvals, evidence and progress are maintained privately. A task is complete only when its expected result has been verified; blocked account work must not stop independent safe engineering.

## Initial sprint

| Phase | Outcome | Evidence needed |
|---|---|---|
| Discovery and baseline | Correct repository/deployment identified, original work preserved, actual framework and integrations understood, critical issues prioritized | Git/deployment records, dated raw/rendered checks, baseline measurements, account-access state and medical evidence gaps |
| Technical foundations | Reliable initial HTML, distinct metadata, canonical URLs, correct sitemap/robots, real status codes and crawlable navigation | Production build, generated-output checks, route/404 tests, rendered-page checks and representative hosting verification |
| Medical/local/on-page | Accurate identity and consultation information; only substantiated patient proof and approved clinical information | Provenance, surgeon review, consent confirmation, NAP/profile review and a distinct keyword-to-page map |
| Release/integrations | Reviewable PR and preview, required production approval, authorized deployment verified, Google properties reused or access gaps documented | PR/preview, test output, approval evidence, actual serving commit and account-specific evidence |
| Monitoring/operations | Tested regression monitoring, one tested daily reporting pipeline, resumable state and client-facing measured report | Workflow/run evidence, delivery evidence, duplicate controls, documented runtime dependencies and comparable measurements |

Adapt the order to impact; do not wait for a calendar day to do an unblocked task. Prioritize P0 availability/indexability, medical misinformation/privacy and severe functional issues, then P1 opportunities. P2/P3 refinements follow the critical work. Production and medical approvals remain required regardless of the deadline.

## Execution cycle

Discover → audit → prioritize → implement → test → verify → document → continue → report.

At each session, read current state and completed work, check repository/deployment status, select the highest-impact unblocked task and finish a concrete reviewable increment. Keep edits on an isolated branch and commit logical changes. Update private state with what changed, where it was tested, measured results, remaining risks and the next action. Record local, preview, production and account-access states separately.

Audit raw HTTP HTML and rendered DOM separately. Validate all important routes, sitemap membership, metadata, canonical consistency, links, schema and consultation paths. Use representative mobile/desktop lab measurements and field data where available; never label lab improvements as real-user results. A Lighthouse SEO score is neither a full SEO audit nor indexing proof.

Research competitors through their own public pages and credible sources. Do not fabricate positions, traffic, backlink counts or search volumes. Prioritize useful commercial/consultation questions and existing-page improvement. No paid backlinks, mass directories or thin generated articles. Verify Google guidance and regulatory requirements when they affect a decision; stored skills may be outdated.

## Coordinated ongoing workflows

**Implementation:** complete outstanding approved source work with persistent task state and test evidence. Keep production publishing gated.

**Deterministic monitoring:** observe uptime, HTTPS/certificates, redirects/status codes, robots/sitemap, metadata/canonicals/index directives, structured-data syntax, broken internal links, consultation links and justified performance samples. Use bounded requests, timeouts/retries, minimal permissions and limited artifact retention. Do not auto-fix production. A scheduled workflow needs activation and a successful test; it is not active merely because YAML exists.

**Intelligent maintenance:** review new evidence, authorized search data and outstanding tasks. Fix justified low-risk issues on an isolated branch and prepare a PR. Remain quiet when a monitoring state is unchanged unless the user’s daily report requires it. Do not invent daily work.

Maintain one authoritative consolidated email pipeline per Asia/Shanghai calendar date at 21:00 (13:00 UTC). Use private recipient/configuration, a date-based report identifier, provider evidence and retry reconciliation to reduce duplicates. Record actual run/delivery times and local execution dependencies. Authentication or missing scheduling is a documented blocker, never simulated success.

## Review cadence

Daily: health/regressions, complete available search data, outstanding tasks and the consolidated report, including no-change days. Weekly: query/page opportunities, local visibility and underperforming content. Monthly: equivalent complete performance periods, core pages, competitor developments and technical health. Use Search Console’s available complete dates and acknowledge reporting lag.

## Acceptance and reporting

The sprint’s private completion record should account for critical issues, crawlable/indexable important pages, metadata/schema, medical review, design/function preservation, mobile evaluation, GitHub review, approved deployment verification, hosting/domain continuity, authorized Google access or exact blockers, tested monitoring/email delivery or exact blockers, persistent state and the client-facing report. Do not declare the full program complete while required approvals or activation evidence are missing.
